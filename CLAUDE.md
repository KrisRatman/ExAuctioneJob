# CLAUDE.md — Биржа услуг (рабочее название: IdeaJob)

> Это рабочий документ-спецификация. Ничего по нему пока не разрабатываем — сначала фиксируем структуру проекта, потом переходим к реализации по этапам (раздел 11).

## 1. Суть проекта

Веб-сервис по типу биржи фриланс-услуг, но в формате **аукциона наоборот**: не исполнитель публикует услугу с фиксированной ценой (как на Kwork), а **заказчик публикует задачу и стартовую цену**, а исполнители сами предлагают свою цену, срок и описание того, как они это сделают. Заказчик выбирает исполнителя из предложивших.

Ключевая механика:
1. Заказчик создаёт заказ (название, описание, теги, стартовая цена) → заказ уходит на доску заказов.
2. Заказ видят только те исполнители, у кого в профиле есть хотя бы один совпадающий тег.
3. Исполнитель открывает заказ и делает предложение (ставку): цена, описание подхода, срок в днях.
4. Заказчик в своём кабинете видит заказ и список предложений, выбирает исполнителя.
5. После выбора — чат между заказчиком и исполнителем, работа выполняется вне жёсткой привязки к площадке (оплата на MVP не встроена, см. раздел 10).

## 2. Роли и регистрация

### Заказчик (Customer)
Простая регистрация: имя, почта/телефон, пароль.

### Исполнитель (Executor)
Регистрация чуть сложнее: имя, почта/телефон, пароль, **теги специализации** (см. раздел 3), **описание о себе** (кто он, чем занимается, опыт).

### Админ (Admin)
Не описан пользователем явно, но нужен технически: управление деревом категорий/тегов, модерация, разрешение споров (раздел 7). Реализуется как Filament-панель — по тому же паттерну, что и в остальных Laravel-проектах (см. раздел 13).

## 3. Система тегов (категорий услуг)

Решение: **фиксированное дерево категорий**, а не свободный ввод тегов. Причина — только так гарантируется точное совпадение "теги заказа" ↔ "теги исполнителя" без разночтений («php» vs «PHP» vs «пхп») и упрощается модерация и SEO (страницы по категориям).

Структура — дерево из 2 уровней: категория → подкатегория (подкатегория и есть «тег», который выбирают заказчик и исполнитель). Пример наполнения (для сидера, дальше пополняется через админку):

- Веб-разработка: Вёрстка (HTML/CSS/JS), WordPress, WooCommerce, Laravel, Другие CMS
- Дизайн: Веб-дизайн (Figma), Логотипы, Баннеры/полиграфия
- Копирайтинг: Тексты для сайтов, SEO-тексты, Посты для соцсетей
- Маркетинг: SMM, Контекстная реклама, SEO-продвижение
- Видео/аудио: Монтаж видео, Озвучка, Обработка звука
- Разработка игр: Unity, 2D/3D-графика, Геймдизайн-документы
- Прочее: то, что не попало в категории выше (чтобы не блокировать создание заказа)

Технически:
- `categories` — таблица с самоссылкой (`parent_id`), поля `name`, `slug`. Категории верхнего уровня (`parent_id = null`) — это группы, показываются как фильтр/группировка в UI; подкатегории (`parent_id` заполнен) — это то, что реально выбирают как тег.
- Исполнитель при регистрации выбирает несколько подкатегорий (multiselect, сгруппированный по категориям верхнего уровня) → `executor_category` (pivot).
- Заказчик при создании заказа выбирает 1–3 подкатегории → `order_category` (pivot).
- **Совпадение = заказ виден исполнителю**, если пересечение множеств тегов заказа и тегов исполнителя не пусто. Реализуется через `whereHas('categories', fn($q) => $q->whereIn('id', $executorCategoryIds))` в ленте заказов исполнителя.
- Управление деревом категорий — из админ-панели (Filament): создание/переименование/перемещение категорий. Пользователи категории не создают, только выбирают из готового списка.

## 4. Заказ: жизненный цикл и статусы

Статусы заказа (`orders.status`):

1. **`open`** («на аукционе») — заказ создан, виден подходящим исполнителям, принимает предложения.
2. **`in_progress`** («в работе») — заказчик выбрал исполнителя, остальные предложения автоматически переводятся в статус `rejected`, отклонённым исполнителям приходит уведомление «заказ отдан другому исполнителю» (чтобы не оставлять их в неведении — решение добавлено при структурировании, не блокирует MVP).
3. **`completed`** («выполнено») — исполнитель отмечает работу сданной, заказчик подтверждает.
4. **`disputed`** («спор») — если заказчик не согласен с результатом на шаге `completed`, он может открыть спор вместо подтверждения.
5. **`resolved`** — спор закрыт решением админа (заказ либо возвращается в `completed`, либо отменяется).
6. **`cancelled`** — заказчик отменил заказ, пока он в статусе `open` (предложений на него ещё нет, либо есть, но заказчик передумал — предложившим исполнителям тоже уходит уведомление).

### Создание заказа (заказчик)
Поля: `title`, `description`, теги (категории, п. 3), `starting_price`. После создания — статус `open`, попадает в ленту подходящих исполнителей.

### Предложение исполнителя (Bid)
Исполнитель видит в общей ленте только заказы, теги которых пересекаются с его тегами. При клике на заказ открывается модальное окно с формой предложения:
- `offer_price` — цена. **Ограничение: не выше `starting_price + 1000 ₽`.** Валидация на бэке и фронте.
- `approach_description` — как исполнитель это сделает.
- `duration_days` — срок выполнения в днях (целое число).

Одно предложение на заказ от одного исполнителя (повторный клик — редактирование своей же ставки, пока заказ ещё `open`).

### Кабинет заказчика
Список своих заказов со статусом и счётчиком предложений («5 исполнителей готовы взяться»). При клике на заказ — двухколоночный экран:
- **Слева** — вся информация по заказу (название, описание, теги, стартовая цена, статус).
- **Справа** — список предложений: исполнитель, цена, срок, **средний рейтинг исполнителя и количество выполненных заказов** (см. раздел 7.1) — чтобы заказчику было проще выбрать. При клике на исполнителя — разворачивается карточка: его теги/описание профиля, рейтинг с последними отзывами, `approach_description` к этому заказу, кнопка **«Принять исполнителя»**.

### Принятие исполнителя
По нажатию «Принять исполнителя»:
1. Заказ → `in_progress`, `executor_id` заказа проставляется.
2. Остальные предложения по заказу → `rejected` (+ уведомление отклонённым).
3. Создаётся диалог (`Conversation`) между заказчиком и исполнителем, привязанный к заказу.
4. Заказчика сразу перекидывает в чат с исполнителем.
5. Исполнителю приходит realtime-уведомление «Вас приняли на заказ „…“» (колокольчик уведомлений). Клик по уведомлению → переход в чат. Либо исполнитель сам переходит через пункт меню «Чат».

## 5. Чат

Простой чат 1:1, привязанный к заказу (`conversation_id` = `order_id`, участники — заказчик и исполнитель этого заказа). Сообщения (`messages`: `conversation_id`, `sender_id`, `body`, `created_at`, `read_at`). Список диалогов в общем разделе «Чаты» + бейдж непрочитанных.

## 6. Уведомления и realtime — Laravel Reverb

Технология подтверждена: **Laravel Reverb** (официальный self-hosted WebSocket-сервер Laravel, бесплатный, нативно работает с `Broadcasting` и `Laravel Echo`).

Как это работает (подробно, т.к. тема не самая тривиальная):
- В `.env` настраивается `BROADCAST_CONNECTION=reverb`, поднимается процесс `php artisan reverb:start` (отдельный процесс рядом с очередями, как `queue:work`).
- События-триггеры оборачиваются в классы, реализующие `ShouldBroadcast` (Laravel-события, не путать с Eloquent-событиями): `NewBidPlaced`, `ExecutorAccepted`, `BidRejected`, `NewMessage`.
- Каждое событие транслируется в приватный канал конкретного пользователя, например `private-user.{id}`, авторизация канала — через `routes/channels.php` (проверка, что слушатель — действительно тот пользователь).
- На фронте `Laravel Echo` (JS-библиотека) подписывается на свой приватный канал через `Echo.private('user.' + userId).listen('NewBidPlaced', …)` и обновляет счётчик уведомлений / список сообщений без перезагрузки страницы.
- Для UI live-обновлений (счётчик предложений, новое сообщение в чате) это будет сочетаться с Livewire: Livewire-компонент слушает broadcast-событие через `#[On('echo-private:...')]` и обновляет часть страницы.
- Уведомления как сущность — стандартный `Illuminate\Notifications\Notification` Laravel (канал `database` + свой broadcast-канал), хранятся в `notifications` таблице, есть готовый колокольчик «непрочитанные».

## 7. Завершение заказа и споры

Выбран вариант **с разрешением споров** (не просто отзыв/рейтинг):
1. Исполнитель отмечает заказ «Сдано» → статус меняется на служебный `delivered` (промежуточный, можно объединить с `completed` на этапе реализации — решить при кодировании).
2. Заказчик видит уведомление, может:
   - **Подтвердить** → статус `completed`, заказ закрыт.
   - **Открыть спор** → статус `disputed`, заполняет причину недовольства.
3. Спор попадает в очередь модератора в админ-панели (Filament): админ видит переписку чата, детали заказа и предложения, принимает решение (вернуть в работу / закрыть как выполненный / отменить).
4. Статус → `resolved` с пометкой решения.

### 7.1. Рейтинг исполнителя

Добавлено по запросу пользователя (изначально в MVP не входило, теперь входит). Логика:

- Рейтинг **односторонний** — только заказчик оценивает исполнителя после выполненного заказа. Обратной оценки «исполнитель оценивает заказчика» нет (не запрашивалась).
- Заказчику предлагается оставить оценку **сразу после перехода заказа в `completed`** (после подтверждения, что всё устраивает — не после спорного `disputed`/`resolved`, чтобы не смешивать конфликтные заказы с обычной статистикой). Оценка необязательна, но форма показывается сама («Оцените работу исполнителя»).
- Форма оценки: `rating` — целое число 1–5 (звёзды), `comment` — необязательный текстовый отзыв.
- Одна оценка на один выполненный заказ (заказчик не может оценить одного и того же исполнителя дважды за один и тот же заказ).
- Хранится в новой таблице `reviews` (см. раздел 8): `order_id`, `customer_id`, `executor_id`, `rating`, `comment`, `created_at`.
- У исполнителя считается **средний рейтинг** (`avg(rating)` по всем его `reviews`) и **количество выполненных заказов** (`count` заказов в статусе `completed`, где он `executor_id`) — оба значения кэшируются в `executor_profiles` (`rating_avg`, `completed_orders_count`) и пересчитываются при создании нового отзыва (пересчёт через модель-обсервер `Review`, не тяжёлый запрос на каждый показ страницы).
- Показывается везде, где заказчик видит исполнителя: в списке предложений по заказу (раздел 4, «Кабинет заказчика»), в развёрнутой карточке исполнителя (звёзды + последние 2–3 отзыва с комментариями), и на публичном профиле исполнителя (если решим делать публичные профили — не обсуждалось, по умолчанию рейтинг виден только в контексте заказа/предложений).

## 8. Сущности (модели БД) — сводка

| Модель | Ключевые поля | Комментарий |
|---|---|---|

## 9. Дизайн

Референсы — **Kwork и FL.ru**, но с оговоркой: убрать всё лишнее (перегруженные фильтры, лишние виджеты, рекламные блоки) — интерфейс должен быть простым и сфокусированным на двух сценариях (создать заказ / откликнуться на заказ).

Палитра: **красно-белая**. Ориентир — акцентный красный (тёплый, не «кровавый», ближе к `#E63946`/`#D7263D`) на белом/светло-сером фоне (`#FFFFFF`, `#F8F9FA`), тёмный текст (`#1A1A1A`) для контраста. Красный — только для акцентов: кнопки основного действия, статусы, активные вкладки; не заливать красным большие площади.

Технически — Tailwind CSS (уже в стеке пользователя) с кастомной палитрой в конфиге, без отдельного дизайн-макета в Figma (пользователь предпочитает вёрстку по готовым макетам, но макета тут нет — значит, потребуется либо накидать самому в Tailwind по референсам, либо сначала набросать в Figma перед вёрсткой — решить перед этапом 4 в разделе 11).

## 10. Что осознанно НЕ входит в MVP

Зафиксировано при структурировании:
- **Оплата/эскроу на площадке.** Заказчик и исполнитель договариваются об оплате сами, вне сайта. Площадка только сводит стороны и даёт чат. Комиссии нет.
- **Отзывы/рейтинг заказчика от исполнителя (обратная оценка).** Рейтинг исполнителя заказчиком — есть (п. 7.1), а обратной оценки «исполнитель оценивает заказчика» нет.
- Мультиязычность, мобильное приложение, партнёрская программа — не обсуждались, считать вне скоупа, пока не будет отдельного запроса.

## 11. Стек

Laravel (актуальная версия, как в остальных проектах — Laravel 13 / PHP 8.4), MySQL, Livewire (интерактивные части: модалка ставки, кабинеты без перезагрузки), Tailwind CSS, **Laravel Reverb** (realtime, п. 6), Laravel Breeze/Fortify (аутентификация с 2 ролями при регистрации), **Filament** (админ-панель: категории, споры, пользователи — тот же паттерн, что в остальных Laravel-проектах пользователя), Pest (тесты), Docker (окружение — по аналогии с остальными проектами).

## 12. MVP и этапы

1. **Этап 1 — каркас и аукцион.** Роли и регистрация (заказчик/исполнитель с тегами и описанием), дерево категорий + сидер + CRUD в Filament, создание заказа с тегами и стартовой ценой, лента заказов для исполнителя (фильтр по совпадению тегов), форма предложения (с валидацией «не выше цены +1000 ₽»), кабинет заказчика (список заказов → карточка заказа с предложениями), принятие исполнителя (смена статусов, отклонение остальных предложений).
2. **Этап 2 — чат и realtime.** Диалог заказчик-исполнитель после принятия, Laravel Reverb, уведомления (принят на заказ / новое сообщение / отклонена ставка), колокольчик уведомлений с переходом в чат.
3. **Этап 3 — завершение, споры и рейтинг.** Статусы «сдано» → «подтверждено» / «спор», админ-панель разрешения споров, форма оценки исполнителя после `completed` (звёзды + отзыв), кэш среднего рейтинга и счётчика выполненных заказов на профиле исполнителя.
4. **Этап 4 — дизайн.** Вёрстка в красно-белой палитре по референсам Kwork/FL.ru, адаптив.
5. **Этап 5 — тесты, README, демо.** Pest-тесты, README со скриншотами (без раздела о планах на будущее — см. п. 13), Docker, деплой демо (по аналогии с остальными проектами — на Beget).
